## Honest state

Generated from incident.io's public OpenAPI spec. Not production-tuned. Use it as a starting
point or a reference.

**Scope.** Generated from the complete published spec — all 121 paths across its three API
versions — with no hand-editing of the spec: 48 entities, 147 operations.

incident.io names every response envelope `<Namespace><Verb>ResultV<N>`, which earlier generator
versions classified as entities in their own right. @voxgig/apidef 6.4.x folds those back
into the resource they wrap. A handful of operations are namespace-only (`Catalog V2`,
`Utilities V1`) or carry an operation namespace matching no path segment
(`/v2/escalation_paths` is served by `Escalations V2#ListPaths`); those are switched off in
`.sdk/model/guide/guide.aontu`, the supported way to correct a classification.

Everything here is reproducible from the spec plus the committed config — clone,
`npm install` in `.sdk/`, `npm run generate`.

**Known rough edge:** entity descriptions come from the spec's operation summaries, so a few
read as terse restatements of the entity name. The spec has no per-schema descriptions.

When teams want SDKs like these production-grade, idiomatic per language, tested, documented,
and released through a real pipeline, Voxgig does that work as a consulting engagement. The
toolkit also generates Java, C#, Swift, Kotlin, Rust and more if your customers need them.

## Entities, not endpoints

This SDK exposes the API as **48 semantic entities** that you
call directly, instead of assembling URL paths and query strings. See the [Entities](#entities) table below for the full list. Entities are
**Capitalised** to mark them as the primary surface, each with the operations they
support (`list`, `load`, `create`, `update`, `remove`):

```ts
const client = new IncidentIoSDK()
const items = await client.Action().list()
```

Thinking in entities keeps the mental model small — for people and AI agents alike —
rather than reasoning about raw HTTP routes and query parameters.

## Use it from an AI agent (MCP)

The generated MCP server exposes every operation in this SDK as an
[MCP](https://modelcontextprotocol.io) tool that Claude, Cursor or Cline
can call directly. Build and register it:

```bash
cd go-mcp && go build -o incident-io-mcp .
```

Then add it to your agent's MCP config (Claude Desktop, Cursor, etc.):

```json
{
  "mcpServers": {
    "incident-io": {
      "command": "/abs/path/to/incident-io-mcp"
    }
  }
}
```

## Direct and prepare

For endpoints the entity model doesn't cover, use the low-level methods:

- **`direct(fetchargs)`** — build and send an HTTP request in one step.
- **`prepare(fetchargs)`** — build the request without sending it.

Both accept a map with `path`, `method`, `params`, `query`,
`headers`, and `body`. See the [How-to guides](#how-to-guides) below.

## Advanced

> Everyday use only needs the sections above. This explains the internals
> behind every call — relevant when writing custom features.

Every SDK call runs the same five-stage pipeline:

1. **Point** — resolve the API endpoint from the operation definition.
2. **Spec** — build the HTTP specification (URL, method, headers, body).
3. **Request** — send the HTTP request.
4. **Response** — receive and parse the response.
5. **Result** — extract the result data for the caller.

A feature hook fires at each stage (e.g. `PrePoint`, `PreSpec`,
`PreRequest`), so features can inspect or modify the pipeline without
forking the SDK.

Pass custom features via the `extend` option at construction time.
